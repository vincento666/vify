# Spec 224: AI Assistant Durable ToolRunner Idempotency And Circuit Breaker

Status: `contract-ready`

## Problem

Spec 222 ToolRunner currently has retry/backoff and circuit breaker semantics,
but the idempotency ledger and breaker state are process-local. That is enough
for a single-process MVP demo, but it is not production-safe across process
restart, multi-worker execution, or fallback adapter transitions.

This spec defines durable semantics before implementation.

## Scope

Include:

- durable ToolRunner idempotency ledger semantics;
- operation identity and idempotency key generation;
- timeout `UNKNOWN` lifecycle, retention, and release authority;
- fallback adapter and primary adapter relationship;
- read-tool vs side-effect-tool behavior;
- session/run-level vs operation-level idempotency;
- persistent circuit breaker state and audit evidence.

Exclude:

- code implementation in Spec 222 corrective wave;
- sandbox isolation, HA worker takeover, multi-tenant infra, or new broker;
- real airline business adapter implementation;
- changing existing public tool schemas unless a later implementation slice
  explicitly accepts that migration.

## Definitions

`operation_id`

Stable identifier for one intended tool operation. It survives retries and
fallback adapter attempts when the intended external effect is the same.

`attempt_id`

Unique identifier for one concrete execution attempt under an operation.

`idempotency_key`

Externally visible or tool-adapter-visible key used to dedupe side effects. It
may be user-supplied, model-planned, or generated by ToolRunner, but must be
persisted before a side-effect attempt starts.

`UNKNOWN`

The runner dispatched an attempt but cannot prove whether the effect happened,
usually because of timeout, connection reset, worker crash, or ambiguous 5xx.

## Required Decisions

### Ledger Granularity

MVP ledger granularity is operation-level with attempt rows:

- one durable `operation` record for the intended tool call;
- zero or more durable `attempt` records for retries and fallback attempts;
- operation status is derived from attempts but persisted for fast recovery.

Production boundary:

- operations must be queryable by session, run, task/plan step, tool name,
  effect class, idempotency key, and operation status;
- attempts must preserve request hash, response hash, error class, timing,
  selected adapter, model/tool budget, and trace span id.

### Key Generation

`operation_id` is generated before execution from canonical fields:

```text
sha256(
  version,
  session_id,
  run_id,
  plan_step_id,
  tool_name,
  effect_class,
  canonical_tool_args,
  supplied_or_generated_idempotency_key
)
```

Rules:

- canonical JSON must sort object keys and normalize insignificant whitespace;
- secret values must be redacted before hashing when the raw secret is not
  needed for dedupe;
- side-effect tools require an idempotency key before first dispatch;
- read tools may use a generated operation id without adapter-visible
  idempotency key;
- retries reuse the same `operation_id`;
- fallback attempts reuse the same `operation_id` when they represent the same
  intended effect.

### UNKNOWN Lifecycle

`UNKNOWN` is a first-class terminal-for-now state.

MVP:

- timeout after dispatch marks attempt `UNKNOWN`;
- side-effect operation with any `UNKNOWN` attempt becomes operation `UNKNOWN`;
- model receives structured observation explaining ambiguity;
- automatic re-execution of side-effect `UNKNOWN` is blocked;
- operator or approved reconciliation tool may resolve `UNKNOWN` to
  `SUCCEEDED`, `FAILED`, or `COMPENSATED`;
- minimum retention: 7 days for side-effect operations, 24 hours for read
  operations.

Production:

- retention and purge policy must be configurable by tool risk class;
- reconciliation must write audit evidence and fencing token;
- unresolved high-risk `UNKNOWN` operations must surface in ops/eval reports.

### Release Authority

The model cannot clear `UNKNOWN`.

Allowed authorities:

- deterministic adapter reconciliation that proves remote state;
- human approval through an audited operator action;
- compensation transaction that marks the operation `COMPENSATED`;
- test-only fixture authority in non-production environments.

Every release must record actor, reason, evidence reference, previous state,
next state, and timestamp.

### Fallback And Primary Relation

Fallback does not create a new intended operation when it serves the same user
intent and same side effect.

Rules:

- primary and fallback attempts share `operation_id`;
- each adapter attempt has distinct `attempt_id`;
- fallback may run after primary `FAILED_RETRYABLE`;
- fallback must not run after primary `UNKNOWN` for side-effect tools unless a
  release authority first resolves the primary state;
- fallback may run after read-tool timeout because read effects are safe to
  repeat unless the tool declares external cost or quota risk.

### Read Tool Vs Side-Effect Tool

Read tools:

- may retry automatically within budget;
- may treat timeout as retryable failure unless the tool declares expensive or
  externally metered reads;
- may cache successful response by request hash;
- may expire ledger records sooner.

Side-effect tools:

- require idempotency key;
- require durable pre-dispatch ledger write;
- block automatic replay when state is `UNKNOWN`;
- require compensation metadata when the adapter supports reversal;
- must emit audit fields for business effect, idempotency key, and
  compensation readiness.

### Session/Run Idempotency Vs Operation Idempotency

Session/run idempotency prevents duplicate user turn submission.

Operation idempotency prevents duplicate tool effects inside a run.

Rules:

- a replayed `messages/async` request returns the original run and does not
  create new operations;
- a resumed or retried run can continue pending operations by `operation_id`;
- operation idempotency must not depend on event sequence numbers;
- operation idempotency survives worker restart and process restart.

### Durable Circuit Breaker

Circuit breaker state is persisted per breaker key:

```text
provider/tool/adapter/risk_class/error_class
```

MVP states:

- `CLOSED`: normal execution;
- `OPEN`: block attempts and return structured observation;
- `HALF_OPEN`: allow limited probe attempts.

Transitions:

- repeated retryable failures or rate limits open the breaker;
- cooldown moves `OPEN` to `HALF_OPEN`;
- successful probe closes the breaker;
- failed probe reopens the breaker;
- operator may force open/close with audited reason.

The breaker state must include failure counters, opened reason, opened at,
cooldown until, last attempt id, actor, and audit span id.

## Acceptance Criteria

- Spec distinguishes MVP acceptable boundary from production boundary.
- Key generation is deterministic and documented.
- `UNKNOWN` state, retention, and release authority are explicit.
- Fallback and primary attempts share operation identity when the intended
  effect is the same.
- Read tools and side-effect tools have separate ledger rules.
- Session/run idempotency and operation idempotency are not conflated.
- Circuit breaker state is durable and auditable.
- Future implementation tasks can be executed slice by slice with RED tests.
